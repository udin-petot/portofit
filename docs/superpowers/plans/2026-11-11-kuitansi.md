# Kuitansi PortoFit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Setiap order yang sudah diverifikasi menghasilkan satu kuitansi bernomor yang bisa diunduh pelanggan dan dikirim ke emailnya.

**Architecture:** Penerbitan terjadi di dalam transaksi verifikasi yang sudah ada, dengan nomor urut per tahun yang dijaga kunci transaksi. Email tidak dikirim di dalam transaksi, melainkan lewat tabel antrean yang diproses cron lima menit. PDF dibuat di server memakai mesin PDF yang sudah ada di `packages/pdf`.

**Tech Stack:** TypeScript, Drizzle ORM, PostgreSQL, oRPC, Hono, nodemailer dan react-email, mesin PDF Forme, Vitest, TanStack Router.

**Spec:** `docs/superpowers/specs/2026-11-11-kuitansi-design.md`

## Global Constraints

- Ini kuitansi, bukan faktur pajak. Tidak ada NPWP. Setiap PDF memuat kalimat "Kuitansi ini bukan faktur pajak."
- Pengirim email tetap `noreply@portofit.tech` lewat Resend. Jangan menambah kredensial Gmail.
- Nomor berbentuk `PF/YYYY/NNNNNN`, contoh `PF/2026/000123`, enam digit dengan nol di depan.
- Semua tanggal dicetak dalam zona `Asia/Jakarta`.
- Semua nominal rupiah memakai pemisah ribuan titik dan awalan `Rp`, tanpa desimal.
- Satu order hanya boleh punya satu kuitansi. Dijaga indeks unik pada `invoice.order_id`.
- Kuitansi hanya terbit untuk order berstatus `lunas`.
- Tidak ada dependensi baru kalau mesin PDF yang ada masih bisa dipakai.

## Review Focus

- Dua admin memverifikasi dua order pada detik yang sama. Harapan: dua nomor berbeda dan berurutan, tidak ada yang gagal karena bentrok.
- Admin menekan verifikasi dua kali pada order yang sama, atau halaman terkirim ganda. Harapan: kuitansi kedua tidak terbit, tidak ada nomor yang terbuang.
- Email gagal karena SMTP mati saat verifikasi. Harapan: order tetap lunas, kuitansi tetap terbit, antrean menyimpan kegagalan dan mencoba lagi.
- Pelanggan membuka kuitansi milik pengguna lain lewat id. Harapan: ditolak, bukan dikirim.
- Order lunas dari sebelum fitur ini ada. Harapan: tidak otomatis mendapat nomor yang menabrak urutan, tapi admin bisa menerbitkan dengan tanggal verifikasi asli.

**Files:**
- Create: `packages/db/src/schema/invoice.ts`
- Modify: `packages/db/src/schema/index.ts` (ekspor `invoice`)
- Create: `migrations/20261111120000_invoice/migration.sql`

**Interfaces:**
- Produces: `invoice`, `invoiceCounter`, `invoiceEmail` (tabel Drizzle), tipe baris `InvoiceRow = typeof invoice.$inferSelect`.

- [ ] **Step 1: Tulis skema**

`invoice`: `id` text PK default `generateId()`, `number` text notNull unique, `orderId` text notNull unique references `billingOrder.id` onDelete cascade, `userId` text notNull references `user.id` onDelete cascade, `issuedAt` timestamptz notNull defaultNow, `snapshot` jsonb `$type<InvoiceSnapshot>()` notNull.

`InvoiceSnapshot` berisi: `customerName`, `customerEmail`, `planName`, `credits`, `amountIdr`, `uniqueCode`, `totalIdr`, `paymentMethod`, `paidAt` (ISO string), `balanceAfter`.

`invoiceCounter`: `year` integer PK, `lastNumber` integer notNull default 0.

`invoiceEmail`: `id` text PK, `invoiceId` text notNull references `invoice.id` onDelete cascade, `toEmail` text notNull, `status` text notNull default `'pending'`, `attempts` integer notNull default 0, `lastError` text, `createdAt` timestamptz defaultNow, `sentAt` timestamptz. Indeks pada `(status, createdAt)`.

- [ ] **Step 2: Tulis migrasi SQL** yang hanya berisi `CREATE TABLE` dan `CREATE UNIQUE INDEX`, tanpa `ALTER` pada tabel lama. Ikuti bentuk migrasi terakhir di folder `migrations/`.
